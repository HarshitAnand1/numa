## Backend interface reconciliation (resolved in code and tests, not live)
The backend's pre-contract proposal differed from what Member 1 shipped. Fixed in `packages/shared`, `packages/sdk-server` and `apps/api`: (1) the `Order` struct is now `{campaignId, merchant, creator, buyer, gross, orderId, deadline}`; (2) `payOrder` passes an explicit `authNonce` computed as `OrderCommitment` (the relayer recomputes it from on-chain `commissionBps` and `feeBps` and never trusts a supplied nonce); (3) the registry is read through `getCampaign(id)` (there is no `merchantOf`); (4) the `OrderSettled` ABI indexes `merchant` and `OrderRefunded` has `merchantPulled`.

## Backend features (Member 2)
- **Relayer:** fixed target, local verification of the buyer's authorization, simulate-first, gas ceiling, daily cap, per-address limit; claim statuses `claimed → sent → settled | reverted`; reconciler resolves timeouts from the chain (`RELAYER.md`).
- **Release keeper:** queues every settlement and calls `release` after the refund window using chain time, never double-sending (`RELAYER.md`).
- **Indexer + Arkiv:** mirrors `OrderSettled` into `numa.conversion`, idempotent by `orderId`; reputation counts only conversions verified against the event (`API.md`).
- **Click tracker:** `/r/:code` counts clicks (hashed visitor) and `demo:fake-clicks` shows 500 clicks next to 0 verified sales (`DEMO.md`).
- **Discovery:** campaigns, trending, creator search, leaderboard, creator card, recommendations, invites (`API.md`, `ARKIV.md`). Seeded with `[DEMO]` data on Rabdi via `seed:demo`; those campaign ids do not exist on-chain and show as unverified.
- **Link resolution and creator offers:** `GET /links/:code` (approved-creator check on-chain, earliest claim wins) and `GET /creators/:address/offers` (own offers with status). Unit-tested with fakes; the underlying Arkiv queries are live-verified.
- **Merchant review:** `GET /campaigns/:id/offers` (offers with creator profile, the merchant's verified decision and on-chain approval); tested with fakes, not run against live Arkiv data for this route.
- **Receipts and export:** `GET /receipts/:orderId` and `GET /merchants/:address/orders` (JSON or accountant CSV), rebuilt from chain events; checked against on-chain balances in the rehearsal.
- **Deploy tooling:** fork rehearsal and a read-only preflight (`DEVELOPMENT.md`); a Render Blueprint (`render.yaml`) and runbook (`HOSTING.md`). **Nothing is hosted yet**; the Blueprint is not validated by Render, and the API image builds and boots locally (the Dockerfile was missing the `sdk-react` package and is fixed).
- **Operational:** CORS allowlist (`CORS_ORIGINS`), discovery timeout (504 after `DISCOVERY_TIMEOUT_MS`), Postgres migrations (001-005), Dockerfile.
- **Negotiation agents** (`AGENTS.md`, ADR 0008, **Proposed**): `numa.agent` and `numa.negotiation` entities, rules engine with private guardrails, signed policy API, verified threads, deal tickets, runner loop (off unless `AGENT_WALLET_PRIVATE_KEY` is set), optional LLM phrasing (Gemini free tier or Claude; template fallback). Feed and status endpoints for the UI (`/agents/threads`, `/agents/binding`) and the shared signed-text builder (`@numa/shared`) are built. Not built: any UI, a live run against a registry.

## Frontend (Member 3)
`apps/web` was generated from Figma (`docs/FIGMA_PROMPT.md`) and revised: non-overlapping hero, larger `numa` wordmark, warmer palette, CSS/JS animation (no animation library; respects `prefers-reduced-motion`), self-hosted fonts.

**Wired to the API (`src/api/`):** typed client for `/discovery/{campaigns,trending,leaderboard}` and `/creators/:address`; `useResource` hook; `DataBadge` shows LIVE / DEMO DATA / SYNCING on every such screen. Rule: demo fixtures appear **only** when the API is unreachable, times out (6s), or returns an HTTP error (or `VITE_DATA_MODE=demo`); a successful empty response is shown as an honest empty state. `merchantVerified: null` is rendered as "unchecked", never "verified"; `score: null` as "No verified sales history yet". Dev: Vite proxies `/api` to `VITE_API_PROXY` (default `http://localhost:8787`).
Verified against the **real** `apps/api` booted locally with throwaway keys: `/discovery/*` returned `[]` and `/creators/:address` returned a no-profile, null-score card, and the UI rendered both correctly. A populated response was verified only against a stand-in server shaped from `routes/discovery.ts`, **not** real Arkiv data (none exists yet, and querying Arkiv without a free access key is heavily rate-limited: the first discovery query hung for ~60s before later ones returned in ~1s).

**Routing:** `src/routes.ts` maps URLs to screens (`/campaigns/:id`, `/creators/:address`, 404 for anything malformed). A static host must serve `index.html` for unknown paths (SPA fallback); Vite dev/preview already do. **Campaign detail** (`/campaigns/:id`) was never reachable or styled in the Figma export (blank page); it now loads the campaign from the API and its offer flow now publishes the offer to Arkiv through the wallet (see "Creator and merchant tools").
**Wallet connect + gasless signing (built, not yet run against a real chain):** the logic lives in `packages/sdk-react` (consumed by `apps/web` and `apps/demo-shop`); the app keeps only its wallet button and chain config in `src/web3/`. Injected wallets only (wagmi), Whitechain network switch, and a checkout at `/checkout/:code?campaign=&creator=&amount=` (the click tracker redirects there). The buyer is asked to sign only after the order service's answer is **verified against the chain**: the order must match what was asked (buyer, creator, campaign, exact amount), the merchant and payout signer must be the campaign's on-chain ones, the campaign must be settleable and the creator approved, and the authorization nonce is recomputed from the on-chain commission and fee and must equal the server's. Then it checks the buyer's USDT balance, signs the EIP-3009 `ReceiveWithAuthorization` (to = router, valid until the order's deadline), and posts to `/relay`. A double-submit guard stops a second payment while one is in flight; a relay timeout or `DUPLICATE` is reported as "outcome unknown, check the explorer" and never offers a blind retry. Real checkout runs only when the router and registry addresses are configured (`DEPLOYED_ADDRESSES` in `@numa/shared`, or `VITE_NUMA_ROUTER_ADDRESS` / `VITE_CAMPAIGN_REGISTRY_ADDRESS`); until then the page is a **labelled SIMULATION**.
Verified: 31 sdk-react + 31 web unit tests (incl. security checks mutation-tested, the signature accepted by the API's real `relayRequest` schema and re-checked the way the relayer checks it, and a drift guard that fails if the relayer adds an error code the UI has no message for), plus a 33-check browser run of the checkout (re-run through the extracted package) and a 16-check run of the demo shop, with a stand-in wallet that really signs, a fake Whitechain RPC and a stand-in API (happy path, double click, wrong network, overcharging server, forged split, insufficient USDT, unapproved creator, declined signature, DUPLICATE, TX_REVERTED). **Not verified:** a real wallet (MetaMask/Rabby), the deployed contracts, the real relayer, or a real USDT transfer. Gasless checkout is still NOT demonstrated.
**Gap for Member 2:** nothing resolves an attribution link `code` to its creator + campaign (`resolveLink` needs both already), so the checkout takes `campaign` and `creator` in the URL. A `GET /links/:code` returning them would let the click tracker's `/checkout/<code>` redirect work on its own.
**Bundle:** wagmi + viem take the web bundle from ~95 KB to ~224 KB gzipped (demo shop: ~112 KB); lazy-loading the wallet layer is a possible follow-up.
**Creator dashboard (`/creator`):** identity is the connected wallet. Overview, discover (matched via `/creators/:address/recommendations`), invites (via `/invites`, inviter shown as unchecked when it can't be verified) and earnings (verified sales from the creator card, held/released from the last 10 sales, CSV export) are read from the API; without a wallet there is a gate and an optional, labelled sample dashboard. The offers, links and profile tabs are **labelled samples**: the API can't list a creator's own offers, and publishing needs wallet signing on Arkiv. A creator with no profile gets an honest empty state (the API's "no profile" 404 is treated as an answer, not an outage). 29-check browser run against a stand-in API.
**Demo shop (`apps/demo-shop`):** "Kiln & Co.", a deliberately unlike-numa store. Takes the campaign from `VITE_CAMPAIGN_ID` and the creator from `?creator=0x…`; says plainly when contracts aren't deployed or no creator link was used; keeps the checkout widget mounted after payment so the receipt stays visible. It uses numa's demo `/orders` route as its order endpoint, so that API must run with `MERCHANT_SIGNER_KEY` set to the campaign's payout signer.
**Agents UI (`/agents`):** one page for creators and merchants. (1) **Binding**: shows the agent wallet from `/agents/status` and the live binding state from `/agents/binding`; binding is an Arkiv transaction signed by the user's wallet (adds the Arkiv network first, loads `@numa/arkiv` lazily, then puts the wallet back on Whitechain), revoking deletes the entity. (2) **Policy form**: the private floor/ceiling, opening offer, auto-accept, step, max rounds and categories, validated by the same rules as the backend's `parsePolicy` (a test runs both over 600 generated inputs and demands identical verdicts) and saved with an EIP-191 signature over `@numa/shared`'s `policyAuthMessage`; the signature is checked in tests by the backend's own `verifyPolicyAuth`. Reading a saved policy back also needs a (read-scoped) signature; nothing is kept in the browser. (3) **Activity feed**: `/agents/threads` polled every 15 s, expandable verified timelines from `/agents/threads/:offerKey`, forged/unverified messages dropped and counted, counterparty notes rendered as plain text. (4) **Deal tickets** (merchant): `/agents/deals` steps the merchant signs on Whitechain.
**Agents UI verified:** 18 unit tests, and a 30-check browser run against a stand-in API that verifies policy writes/reads with the backend's own validators and a stand-in wallet that really signs. **Not verified:** an actual Arkiv binding write (the test wallet has no tGLM on Rabdi, so the real Arkiv writer correctly refused before asking the wallet to sign; the declined/confirmed paths of that write are untested), the deal-ticket transactions against a deployed registry, and any of it against the real running API with the agent runner.
**Creator and merchant tools (built, run only against stand-ins):** (a) Creator: **profile** (publish to Arkiv; an existing profile only supports availability/min-ask update and a 90-day renew, because name/bio/niche can't be patched), **links** (publish a link for a campaign, saved codes kept per wallet in localStorage, and per-link stats from `/links/:code/stats`: clicks and unique visitors are shown as "earn $0" and only chain-verified sales/commission count), and **offer publish** from the campaign page (72h, wallet-owned). (b) Merchant (wallet-gated): **create campaign** (`createCampaign` on the registry, then the Arkiv listing; the campaign id is read from the on-chain `CampaignCreated` event; if only the Arkiv half fails the UI says the campaign exists on-chain and offers a retry that sends no second transaction) and **review offers** (approve = `approveCreator` on-chain then an Arkiv decision carrying the tx hash, with a retry that sends no second approval; reject = Arkiv decision only). Writes use the shared wallet layer (`web3/arkivWallet.ts`), which refuses with "Insufficient tGLM" before asking the wallet to sign. Tabs still showing sample data carry a visible "sample" tag.
**Tools verified:** 64 web unit tests, and a 51-check browser run with a stand-in wallet, a fake Whitechain RPC that returns a real-shaped `CampaignCreated` receipt, a recording fake of the Arkiv module and a stand-in API; the calldata the wallet is asked to send is decoded with the project's real registry ABI. **Not verified:** any real Arkiv write (no tGLM-funded wallet), the deployed registry, and a real wallet. The real `@numa/arkiv` call signatures are exercised only through the fake. **Also built (stand-in verified, 19-check browser run + 5 unit tests):** the **verify page** (`/verify`) now reads `GET /receipts/:orderId` (settlement from the router, via the API); it accepts an order id or a transaction hash (a tx hash is resolved by reading its `OrderSettled` log from Whitechain), and says "no settled order found" or "couldn't check" instead of showing a match; demo labels like `NMA-8821` are refused with an explanation. The merchant **orders** tab reads `GET /merchants/:address/orders` (with CSV link). Merchants get a **refund allowance** card (reads `USDT.allowance(merchant, router)` from chain and sends `USDT.approve(router, amount)`, ADR 0001). **Not verified:** any of this against the deployed router/USDT or the real API. Merchant overview/creators/invites/settings and the creator "offers" tab are still **samples**.
